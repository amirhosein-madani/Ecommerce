# تفاوت چهار درگاه پرداخت: ZarinPal، Zibal، NextPay، IDPay

هر چهارتا از نظر جریان کلی یکسان‌اند:
`payment_request → redirect به صفحه‌ی درگاه → callback → payment_verify`

اما در جزئیات پیاده‌سازی با هم فرق دارند:

## ۱. جای احراز هویت

| درگاه | روش احراز هویت |
|---|---|
| ZarinPal | `merchant_id` در بدنه‌ی JSON |
| Zibal | `merchant` در بدنه‌ی JSON |
| NextPay | `api_key` در بدنه‌ی فرم (form-encoded، نه JSON) |
| IDPay | `X-API-KEY` در هدر درخواست + `X-SANDBOX` در هدر برای حالت تست |

## ۲. اسم شناسه‌ی تراکنش

| درگاه | نام فیلد |
|---|---|
| ZarinPal | `authority` |
| Zibal | `trackId` |
| NextPay | `trans_id` |
| IDPay | `id` (به‌علاوه یک `track_id` عددی جدا که فقط در پاسخ verify برمی‌گردد) |

## ۳. تشخیص موفقیت/شکست

| درگاه | محل و منطق تشخیص |
|---|---|
| ZarinPal | فیلد عددی `code`/`data.code` در بدنه‌ی JSON؛ مستقل از HTTP status |
| Zibal | فیلد عددی `result` در بدنه‌ی JSON؛ ۱۰۰ موفق در هر دو مرحله، ۲۰۱ یعنی «قبلاً هم تایید شده بود» |
| NextPay | فیلد `code`، اما با دو معنای متفاوت در دو مرحله: مرحله‌ی توکن `-1` یعنی موفق، مرحله‌ی verify `0` یعنی موفق و `-1` یعنی در انتظار — نکته‌ی خطرناک، اگر ندانی باعث پذیرفتن پرداخت‌های ناموفق می‌شود |
| IDPay | خودِ HTTP status code: ۲۰۱ برای درخواست موفق، ۲۰۰ برای verify موفق؛ جزئیات خطا در فیلد جدای `error_code`/`error_message` |

## ۴. مسئول ساخت URL نهایی پرداخت

| درگاه | نحوه‌ی ساخت لینک |
|---|---|
| ZarinPal | فقط `authority` می‌دهد؛ لینک را خودت با یک الگوی ثابت (`start_url + authority`) می‌سازی |
| Zibal | فقط `trackId` می‌دهد؛ همان الگو |
| NextPay | فقط `trans_id` می‌دهد؛ همان الگو |
| IDPay | خودش لینک کامل صفحه‌ی پرداخت را در پاسخ برمی‌گرداند (`link`)؛ باید هم `id` هم `link` را نگه داری، نه فقط یکی |

## ۵. پارامترهای لازم برای verify

| درگاه | چه چیزی باید بفرستی |
|---|---|
| ZarinPal | `authority` + `amount` |
| Zibal | فقط `trackId` — چک مبلغ باید خودت جداگانه انجام بدهی، درگاه خودش این کار را نمی‌کند |
| NextPay | `trans_id` + `amount` |
| IDPay | هم `id` هم `order_id` با هم — تنها درگاهی که به دو شناسه‌ی هم‌زمان نیاز دارد |

## جمع‌بندی

از نظر **جریان کلی** هر چهارتا یکسان‌اند، اما در **جزئیات پروتکل** — جای auth، اسم فیلدها، معنای کدهای وضعیت، و مسئولیت ساخت URL — با هم فرق دارند. این دقیقاً همان چیزی است که یک اینترفیس مشترک (`BasePaymentGateway`) باید انتزاع کند؛ ولی همان‌طور که در IDPay دیدیم، بعضی تفاوت‌ها (مثل برگرداندن لینک کامل به‌جای فقط یک شناسه) می‌توانند سیگنیچر متدها را هم تحت تأثیر قرار دهند، نه فقط اسم فیلدها را.
